What exists today

Native What it can do today

  • Add a Devin label to a Jira ticket → Devin scopes it, comments with a plan + confidence estimate (red/yellow/green), then you click to start a session
  • Bulk-label multiple tickets to scope in parallel
  • Two-way: Jira label triggers Devin session mapped to a playbook (Citi has this via Moritz Stephan)

Gaps What it cannot do

  • Reliably “look at a Jira board” and scan/prioritise tickets autonomously
  • Send off sequential Jira tickets automatically (plan A → complete → move to B)
  • Trigger from arbitrary labels (only Devin label) — customers have asked for custom prefixed labels like Devin-Support
Workaround: Atlassian / Jira MCP

Most customers are using the Jira MCP from the marketplace instead. This gives Devin read/write access to Jira within sessions via natural language — query boards, read tickets, update status, post comments. Brian Smitches shipped a PR adding a callout on the native Jira settings page recommending users also add the MCP.

Capability Native Integration Jira MCP
Trigger Devin from Jira ticket Yes (label-based) No (session-initiated)
Read/query a Jira board No Yes
Create/update tickets in-session Limited Yes
Map playbook to label Yes (Citi pattern) No
Sequential ticket workflows No Possible (within one session)

What CTaima specifically wants vs. what’s possible

For CTaima’s ask of “plan Jira tickets where Devin can send off sequential Jira tickets”:

  • Today: You’d need a custom Jira Automation (webhook) → Devin Session API → Atlassian MCP. Shawn Azman described this exact pattern: “a custom Jira Automation that used the Devin Session API to be triggered from a ticket on either a custom label or specific string match in a comment.” It’s doable but bespoke.
  • Bobby’s demo video (Jan 7) specifically showed: “Devin’s ability to build Jira tickets from scratch and simultaneously begin to work on those tickets via ONE session” and “multiple PRs can be generated from one Session/multiple Jira tickets created and also updated from just one session” — so within a single session, Devin can create + work multiple Jira tickets.
  • For the “read the board” part: The Jira MCP lets Devin query Jira boards, read tickets, and filter — so this is possible today through MCP, just not through the native integration.

Bottom line for your reply to Osmin

The native integration is getting a revamp (confirmed, no date), but today the answer is: use the Jira MCP for board-reading and session-level ticket interaction, and the native integration for label-triggered automation. For sequential ticket workflows, the Devin Session API + Jira Automation webhooks is the path — or wait for the revamp to bring it closer to Linear parity. The Automations/Advanced Devin launch from today’s All Hands could also be relevant here as it enables event-driven agent orchestration.

Here’s the full picture of what you can enable for CTaima with MCP + the broader Devin platform — layered from simplest to most powerful:

Layer 1
Available Now

Atlassian/Jira MCP (Enable in MCP Marketplace — 1 click)

This is the foundation. Once enabled, every Devin session gets read/write access to their Jira instance. Devin can:

  • Query boards & tickets via JQL — filter by project, sprint, status, assignee, labels, priority, custom fields
  • Read full ticket details — description, comments, attachments, subtasks, linked issues
  • Create new tickets from scratch (Devin can decompose a feature into subtasks and create them)
  • Update tickets — change status, add comments, transition workflows, update fields
  • Search across projects — find related issues, duplicates, dependencies

This alone covers CTaima’s “read the board and scan/prioritize tickets” ask — Devin can read their Jira board, analyze tickets, and provide prioritization in a single session.

Layer 2
Available Now

Playbooks (Codify the Workflow)

Create purpose-built playbooks that tell Devin exactly how to work with their Jira board. Examples:

!jira_triage playbook — “Read the Jira board for project X, filter tickets in ‘To Do’ status, analyze each one against the codebase, and rank them by implementation confidence (green/yellow/red). Comment your analysis on each ticket.”

!jira_implement playbook — “Read Jira ticket {ticket_id}, understand the requirements, implement the changes, create a PR, then update the Jira ticket status to ‘In Review’ and add a comment with the PR link.”

!jira_sequential playbook — “Read the Jira board for project X. Find all tickets labeled ‘devin-batch’. Work through them sequentially: for each ticket, read it, implement changes, create a PR, update the ticket status, then move to the next ticket.”

The key insight: within a single Devin session + Jira MCP, Devin can already work through multiple tickets sequentially. Bobby’s demo showed exactly this — one session creating multiple PRs from multiple Jira tickets. The MCP gives Devin the ability to read what’s next and update status as it goes.
Layer 3
Available Now

Native Jira Integration + Label Triggers (Parallel Scoping)

Set up the native integration alongside the MCP:

  • Create dedicated Jira account for Devin
  • Connect in Settings > Integrations
  • Use the Devin label (or any label containing “devin” as a standalone word, e.g., devin-task, Devin-Support) for automatic scoping

Note: The native integration now supports word-boundary matching (case-insensitive), so devin-support or devin-task will trigger it. This partially addresses the custom label request. Labels like devinworkshop (no boundary) won’t trigger.

This gives them parallel bulk scoping — add the label to 20 tickets at once and get confidence scores + plans on all of them.

Layer 4
Custom Setup

Devin Session API + Jira Automation (Event-Driven Sequential Workflows)

This is the most powerful setup for “send off sequential Jira tickets automatically”:

Architecture:

  • Jira Automation rule → When a ticket transitions to a specific status (e.g., “Ready for Devin”) or gets a specific label
  • Webhook action → Calls POST https://api.devin.ai/v3/organizations/{org_id}/sessions with:
    • The ticket details in the prompt
    • A playbook_id pointing to their implementation playbook
    • structured_output_schema to get back structured results (success/failure, PR URL, etc.)
  • Devin session runs → Reads the ticket via MCP, implements, creates PR, updates ticket
  • On completion → Jira Automation can watch for the status update Devin made, then trigger the next ticket
// Example API call from Jira Automation webhook
{
  "prompt": "Implement Jira ticket PROJ-123. Read the full ticket
    details from Jira, implement the changes, create a PR, and
    update the ticket status to 'In Review'.",
  "playbook_id": "pb_xxx",
  "structured_output": {
    "type": "object",
    "properties": {
      "ticket_id": {"type": "string"},
      "pr_url": {"type": "string"},
      "success": {"type": "boolean"},
      "notes": {"type": "string"}
    }
  }
}
Layer 5
Power Feature

Advanced Mode + Batch Sessions (Orchestrator Pattern)

The most powerful option — use Advanced Mode as the orchestrator:

  • Start a single Advanced Mode session with a prompt like: “Read the Jira board for project X. Find all tickets in ‘Ready for Devin’ status. For each ticket, create a child Devin session with the !jira_implement playbook to work on it.”
  • Advanced Mode can use batch mode to spawn child sessions in parallel — each one gets its own Jira MCP access, works on its own ticket, creates its own PR
  • The parent session can monitor child session progress and report back

This gives you parallel execution across tickets rather than sequential, which is dramatically faster.

Layer 6
Power Feature

Scheduled Sessions (Autonomous Board Scanning)

Set up a recurring scheduled session (e.g., daily at 9am) with the !jira_triage playbook:

  • Devin scans the board automatically every day
  • Triages new tickets, adds confidence scores
  • Optionally kicks off implementation sessions for green-light tickets
  • Reports results to Slack
Recommendation for CTaima

What I’d Recommend for CTaima Specifically

Minimum viable setup (can do today in ~30 min):

  • Enable Atlassian MCP from marketplace
  • Create a !jira_implement playbook
  • Create a !jira_triage playbook
  • Set up native Jira integration for label-based scoping

Full power setup (needs their API key + some Jira Automation config):

  • All of the above PLUS
  • Jira Automation webhook → Devin API for event-driven session creation
  • Scheduled session for daily board triage
  • Advanced mode batch sessions for parallel ticket processing
The MCP is the linchpin — it’s what transforms every session from “Devin can only see what you paste in the prompt” to “Devin has full read/write access to your entire Jira workspace.” Everything else layers on top of that foundation.
